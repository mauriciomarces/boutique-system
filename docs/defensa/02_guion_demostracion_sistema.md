# Guion de demostración del sistema

## Preparación previa

**Versión principal para defensa: 25 minutos.** El recorrido compacto de 13 minutos que aparece más abajo sirve para ensayos breves. El guion ampliado diferencia las reglas de correlación de CART y propone una comparación normal/anómala. Este archivo es un guion, no evidencia de que se haya realizado una demostración visual end-to-end. Antes de presentarlo, ensayar en una instancia aislada y confirmar health checks, usuario con permisos, datos ficticios y artefacto de modelo cargado.

1. Iniciar solamente el perfil de demostración configurado con bases exclusivas. No reutilizar la base o volúmenes del entorno de trabajo.
2. Revisar la vista previa del generador, luego cargar `--service all --count 3 --seed 42 --scenario both` con `--apply` y confirmación explícita. Las conexiones `DEMO_*` deben apuntar a bases `_demo`, `_test` o `_integration`; el almacén de correlación debe estar en una carpeta temporal dedicada. Instrucciones completas: [README del generador](../../backend/scripts/demo-data/README.md).
3. Los usuarios sembrados quedan inactivos, no tienen credenciales y reciben un rol ficticio sin permisos. Para iniciar sesión use un usuario de prueba previamente provisionado de forma segura; no cree una contraseña conocida ni restablezca cuentas.
4. El script no inserta análisis ni notificaciones. Esos resultados se obtienen ejecutando la clasificación real y, si el resultado es `ANOMALO`, el Gateway pide crear la notificación.
5. Definir antes el orden de limpieza; ejecutar la limpieza optativa solo por el seed de demostración y siguiendo el mismo README. No borrar bases, tablas ni volúmenes.

## Guion detallado de defensa (25 minutos)

### Aporte académico que se debe defender

Presentar el aporte como una **integración experimental y explicable**, no como la invención de CART ni como un detector probado de fraude:

> “El aporte del proyecto es conectar eventos operativos de una boutique con un proceso trazable de análisis. Primero se relacionan los eventos con reglas temporales explícitas; después se transforman en características y un árbol CART entrenado clasifica el vector. La persona puede revisar tanto los eventos y reglas como las preguntas reales del árbol que llevaron a la hoja final. La solución es un prototipo de apoyo a revisión: el conjunto de entrenamiento y las etiquetas son sintéticos, por lo que una clasificación anómala no demuestra fraude.”

### Cómo explicar técnicamente el aporte

1. **Hechos observables:** cada servicio emite un evento con `event_id`, servicio, tipo, entidad, resultado y timestamp. El correlador valida y persiste; no se infiere una regla a partir de texto libre.
2. **Correlación determinista:** ordena/deduplica eventos, aísla el actor, evalúa ventanas y relaciones con condiciones explícitas. R1–R6 son resultados legibles de esa lógica.
3. **Transformación:** las reglas y el historial producen 30 características; el contrato de predicción se valida y 16 columnas entran a CART. Las reglas no son columnas que se entregan como “decisión” al árbol.
4. **Clasificación supervisada:** el artefacto `DecisionTreeClassifier` vigente separa `NORMAL`/`ANOMALO`; Gini mide la mezcla de etiquetas en cada nodo, y el algoritmo elige cortes que reducen la impureza ponderada. La configuración actual limita profundidad a 5 y hojas a un mínimo de 5 muestras.
5. **Explicación individual:** el backend obtiene `decision_path` del árbol cargado y devuelve valor, umbral, condición, rama y hoja. Las importancias globales describen el modelo en conjunto; no reemplazan el recorrido de esta predicción.
6. **Acción prudente:** la alerta se genera después de la clasificación `ANOMALO`. Es una señal priorizada para revisión, no una conclusión legal ni una prueba de fraude.

Como respuesta a “¿cuál es exactamente el aporte?”, decir: “No propongo un algoritmo CART nuevo. Aporto un prototipo que conecta operaciones, correlación temporal explícita y una clasificación interpretable, y permite rastrear el resultado hasta eventos y divisiones del modelo. La evaluación actual es sintética; medir utilidad real queda como trabajo futuro.”

### Ensayo de los dos casos

- **Normal:** usar eventos sintéticos del mismo actor, con venta y salida de stock enlazadas por `venta_id`. Confirmar que no se cuentan actores mezclados y que la salida ocurre después de la venta. Ejecutar el clasificador; reportar literalmente clase, nivel y recorrido recibidos.
- **Anómalo controlado:** seleccionar el actor sintético correspondiente; verificar los cinco fallos, tres anulaciones y tres acciones administrativas dentro de sus ventanas. Ejecutar el mismo flujo y comparar primero reglas/características y luego CART. En una instancia local que ya tenga varios seeds, filtrar por ID de evento `demo-<event-seed>-anomalous-` o por el actor visible en la tabla; no asumir que el ID numérico será idéntico en otra instalación.
- Para ambos casos, abrir la notificación solamente si el Gateway la creó. El generador no escribe análisis/notificaciones directamente; así se demuestra la ruta real y se evita fingir un resultado.

## Escenarios de comparación

### Normal

El generador crea una secuencia ficticia de `VENTA_CREADA` y `STOCK_MODIFICADO` correlacionada por `venta_id`, actor compatible y diferencia inferior a 15 minutos. Para una reproducción aislada del artefacto actual, el ejemplo de [capítulo de IA](./04_explicacion_inteligencia_artificial.md#ejemplo-reproducible-del-modelo-vigente) clasifica una venta con salida de stock como `NORMAL`. Es un ejemplo sintético reproducible, no una conclusión sobre ventas reales.

### Anómalo controlado

El fixture de eventos crea, para un actor sintético, cinco `LOGIN_FALLIDO`, tres `VENTA_ANULADA` y tres `USUARIO_MODIFICADO` dentro de las ventanas de R1, R2 y R5. El script no modifica usuarios reales ni anula compras/ventas de negocio. La clasificación CART se calcula aparte; las reglas no sustituyen al modelo. El resultado mostrado debe leerse como “requiere revisión”, nunca como fraude demostrado.

## Funcionalidades que no se deben prometer

- No hay registro de análisis ni notificación ficticia preparado por el seed; ambos dependen del flujo real.
- `POST /train` responde `409` durante la validación experimental. No mostrar el dashboard como prueba de reentrenamiento activo.
- No se verificó un envío real de correo ni un login end-to-end contra un stack aislado durante este trabajo.
- El flujo de cancelación de compras/ventas existe, pero no es necesario para la demostración principal. No usarlo para generar una anomalía: una cancelación legítima no es prueba de irregularidad.
- No afirmar que las ventas conservan una fotografía inmutable del nombre del cliente. El reporte resuelve el nombre mediante la relación actual con `clientes`.
